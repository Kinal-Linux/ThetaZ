# ThetaZ / "C~" — Wine & Proton GE Study Notes

Study of `Wine/` (official Wine, HEAD) and `ProtonGE/` (GE-Proton11-3) for the goal of
building our own all-purpose Windows compatibility layer.

## 1. Big picture

Wine = "Windows on Unix" via 4 cooperating layers:

1. **`wine` loader** (`loader/main.c`) — a tiny ELF executable. Reserves the Windows
   address space, dlopens `ntdll.so`, calls `__wine_main(argc, argv)`.
2. **wineserver** (`server/`) — a separate Unix daemon (one per WINEPREFIX). Acts as
   the "kernel": owns processes/threads/objects/synchronization/registry/windows.
   ntdll talks to it over a local socketpair using a fixed binary request protocol.
3. **ntdll** (`dlls/ntdll/`) — the heart. Split into a **PE** side (pure-Windows code:
   Rtl*, Ldr*, heap, APC, etc.) and a **unix** side (`dlls/ntdll/unix/`, the `.so`):
   virtual memory, threads, signals→exceptions, syscalls, server IPC.
4. **All other DLLs** (`dlls/*`) — user32, kernelbase, win32u, etc. Each is built as
   a PE file (Windows-facing) + optionally a unix `.so` (private unix backend)
   reachable via the `__wine_unix_call` mechanism.

Everything the PE side can't do with pure user code is implemented in the unix side
or forwarded to wineserver.

### Startup chain (executable launch)
```
shell: wine winword.exe
  loader/main.c: main()
    init_reserved_areas()                      # mmap PROT_NONE low 8GB + top-down zone
    dlopen("dlls/ntdll/ntdll.so"); dlsym("__wine_main")
      __wine_main (dlls/ntdll/unix/loader.c:2102)
        init_paths()                           # dll_dir, system dirs, WINEPREFIX
        check_command_line()                   # --version, --server, etc.
        set_max_limit()                        # RLIMIT_NOFILE/AS/NICE
        virtual_init()                         # build the Windows address space map
        init_environment()                     # env block, DOS env
        start_main_thread()                    # the "first thread"
          virtual_alloc_first_teb()
          dbg_init()
          server_init_process()                # connect to wineserver, init_first_thread req
          virtual_map_user_shared_data()       # KUSER_SHARED_DATA page
          init_cpu_info(); init_files(); init_startup_info()
          init_thread_stack(teb,0,0,0)         # PEB/TEB + stack setup
          NtCreateKeyedEvent(...)              # ntdll global keyed event
          load_ntdll()                         # map PE ntdll.dll, patch exports
          load_apiset_dll()                    # ApiSetMap from apisetschema.dll
          server_init_process_done()           # finish init; start the app
```

After PE ntdll is loaded, its exported functions (patched in `load_ntdll_functions`)
become the real entry points: `LdrInitializeThunk`, `KiUserExceptionDispatcher`,
`__wine_syscall_dispatcher`, `__wine_unix_call_dispatcher`, `RtlUserThreadStart`...

## 2. PE ⇄ Unix interop: `__wine_unix_call`

Header: `include/wine/unixlib.h`.

- A unix lib (`.so`) exports:
  - `__wine_unix_lib_init()` — optional init
  - `__wine_unix_call_funcs[]` — array of `unixlib_entry_t` (NTSTATUS (*)(void *args))
  - optionally `__wine_unix_call_wow64_funcs[]` — same but for 32-bit callers in wow64
- A PE dll that wants the unix backend holds:
  - `__wine_unixlib_handle` — set by ntdll at load time to the `.so`'s funcs table
  - `__wine_unix_call_dispatcher` — pointer to the transition thunk
  - `WINE_UNIX_CALL(code, args)` → `__wine_unix_call(handle, code, args)`
- The PE side sends a "unix call" (like a syscall); the dispatcher switches to the
  unix stack (TEB->GdiTebBatch holds `struct teb_data` with syscall_frame etc.),
  calls `funcs[code](args)`, and switches back.

The ntdll unix funcs table (`loader.c:1008`):
```
0 load_so_dll
1 unwind_builtin_dll
2 wine_dbg_write
3 wine_server_call
4 wine_server_fd_to_handle
5 wine_server_handle_to_fd
6 wine_spawnvp
7 system_time_precise
```

## 3. Syscalls: the Windows SSDT model

- ntdll.spec declares each syscall: `@ stdcall -syscall=0x0048 NtCreateEvent(...)`.
  `-private ZwXxx` aliases map to the NtXxx.
- The unix side builds `KeServiceDescriptorTable[4]` (`unix/syscall.c:246`) with
  `syscalls[]` (function pointers) + `syscall_args[]` (arg byte counts), from the
  generated `ALL_SYSCALLS` macro (`ntsyscalls.h`, generated by `tools/make_syscalls`).
- The actual NtXxx implementations live in the **unix** side, e.g.
  `NtCreateEvent` in `unix/sync.c:1091`.
- Unimplemented syscalls are `SYSCALL_STUB`s that raise `EXCEPTION_WINE_STUB`
  (a debugger/`__wine_stub` exception, `stub_syscall` at `unix/syscall.c:207`).
- The PE ntdll exports thin stubs that jump to `__wine_syscall_dispatcher`
  (asm in `unix/signal_*.c`); the dispatcher loads the syscall frame
  (`struct syscall_frame` in `unix/thread.c`), indexes the table, calls the unix fn,
  restores the frame. The frame lives at a fixed TEB offset so NtGetContextThread can
  read/write the interrupted context (`signal_x86_64.c:1111`).
- `KeAddSystemServiceTable()` allows other modules to add tables (index 0..3,
  12-bit per table).

## 4. wineserver

### Process layout
- Master socket + lock in `/tmp/.wine-<uid>/server-<dev>-<ino>/`.
- `server/main.c`: sock_init → open_master_socket → init_signals/memory/directories/
  threading/registry → `main_loop()`.
- `main_loop` (`server/fd.c:920`): epoll (`main_loop_epoll`) else poll; timeout from
  `get_next_timeout()` (binary-heap/sorted timers, absolute + relative lists);
  `fd_poll_event` dispatches I/O readiness.

### Object model (`server/object.h`, `object.c`)
- `struct object { refcount; handle_count; ops; wait_queue; name; sd; is_permanent; }`
- `object_ops`: size, type (type_descr), dump, init, add_queue/remove_queue (wait),
  signaled/satisfied, signal, get_fd, get_sync, map_access, get/set_sd,
  get_full_name, lookup_name, link_name/unlink_name, open_file, close_handle, destroy.
- Handles: `server/handle.c`, per-process handle table; handles are small ints into
  the table with access masks.
- Named objects resolved in a namespace tree (`lookup_named_object`, root_directory).
- Lifetime: `alloc_object` (ref=1) → `grab_object`/`release_object`; destroy when
  refcount→0; permanent objects (like \BaseNamedObjects) kept alive.

### Request protocol (`server/protocol.def` → `include/wine/server_protocol.h`)
- `tools/make_requests` generates structs from the `.def`.
- `request_header { req; request_size; reply_size }`, `reply_header { error; reply_size }`.
- Fixed-size union `generic_request`/`generic_reply`; variable data read separately.
- `call_req_handler` (`request.c:271`) → `req_handlers[req](&req, &reply)`.
- Threads talk over a socketpair; request_fd + reply_fd; fds passed via SCM_RIGHTS
  (`receive_fd`/`send_fd`).
- `SERVER_START_REQ(init_first_thread)` etc. in ntdll unix/server.c set up the pair.

### Threads/sync
- `server/thread.c`: thread select/wake; a thread waits on a list of objects
  (`wait_queue_entry`); `signaled()/satisfied()` decide wake; APCs (queue_apc).
- Events/mutants/semaphores/timers (timer.c) are named kernel objects.
- `server/fd.c`: file objects ↔ unix fds, fd cache, async I/O (`async.c`).

### Registry (`server/registry.c`)
- In-memory key tree; persisted as `.reg` text files (system.reg, user.reg).
- `registry_key` objects, HKEY special handles (HKEY_LOCAL_MACHINE etc.) as
  pseudo-handles, `HKEY_HANDLE_*`.

### Windows (`server/window.c`, `queue.c`, `winstation.c`)
- Desktop/window-station/window objects; server-side message queues; visible region
  tracking; window z-order; the input thread on the client side (user32/win32u).

## 5. The address space (`dlls/ntdll/unix/virtual.c`)

- `address_space_limit = 0x7fffffff0000`.
- Reserved zones: low 8GB (0x1000..0x200000000) for 32-bit, and the top-down zone
  0x7ffffe000000..0x7fffffff0000; the rest is mapped on demand.
- Windows-facing mmaps are placed in these zones with exact Windows semantics
  (PAGE_*, SEC_IMAGE etc.); VPROT flags track state.
- `virtual_map_builtin_module` maps PE files as SEC_IMAGE.
- WoW64: `virtual_map_user_shared_data`, `map_dosmem` for the 64k/1MB DOS memory,
  `dosmem_size` allocation at low addresses.

## 6. Exceptions (SEH) via Unix signals (`unix/signal_*.c`)

- SIGSEGV/others → `segv_handler` (`signal_x86_64.c:2278`) → build `EXCEPTION_RECORD`
  (AV with rw info), call `virtual_handle_fault` / `dispatch_exception`.
- `struct syscall_frame` is used to save/restore CONTEXT on syscall entry.
- GSBASE/FSBASE management per-thread; TEB lives at GS base.
- `__wine_syscall_dispatcher` asm glue; `__wine_unix_call_dispatcher` likewise.
- `KiUserExceptionDispatcher` (PE) runs RtlDispatchException → per-frame handler
  chain → RtlUnwind. `__TRY/__EXCEPT` map to `ntdll_set_exception_jmp_buf`.
- Cross-signal async: SIGUSR1/2 blocked in server_block_set; `async_raise` used for
  APCs and debug events.

## 7. Proton GE

- `proton` (Python script) is the compatibility tool entry:
  - `Proton` class locates dist files (`base_dir` = the tree).
  - `CompatData` manages the per-game prefix (compatdata/<appid>): pfx dir, upgrade,
    builtin lib copy, symlinks, registry fixups, `setup_prefix()`.
  - `Session` sets env (WINEARCH=wow64 when PROTON_USE_WOW64=1, WINEPREFIX, dlloverrides
    including builtin `steam.exe`, dxvk/vkd3d lib paths via WINEDLLPATH/LD_LIBRARY_PATH),
    then runs the game with `run_proc`.
  - Uses `protonfixes` (umu-protonfixes) per-game overrides; `winecfg`-style config
    via `compat_config` (STEAM_COMPAT_CONFIG).
- `wine/` submodule = Valve's Wine fork; `wine-staging` = staging patchset.
- `patches/` = GE's build patches: proton-prep (applies Valve staging patches),
  wine-hotfixes (applied to wine source), game-patches (applied by game ID), dxvk,
  video-rework, ds5-haptic, openxr etc.
- Graphics layers: dxvk (D3D11/10/9 → Vulkan), dxvk-nvapi (NVAPI), vkd3d-proton
  (D3D12 → Vulkan), d7vk (D3D7/8/9), vklayers, OpenXR-SDK + wineopenxr, openvr.
- Platform shims: lsteamclient, vrclient_x64, steam_helper, umu_helper, FEX (arm64
  x86 emulation), discord-rpc-bridge.

## 8. Reimplementation checklist (what a from-scratch layer must have)

- [ ] ELF loader + reserved address space bootstrap
- [ ] PE loader: headers, imports, relocations, TLS, SEH tables, delayed imports
- [ ] PE→unix call bridge (`unixlib`), per-dll backend .so
- [ ] Syscall table + dispatcher with frame save/restore (SSDT-like)
- [ ] Server daemon: object/handle model, request protocol, process/thread/sync
- [ ] ntdll: PEB/TEB, heap, Rtl*, Ldr*, APCs, keyed events, virtual memory
- [ ] Signal→exception bridge + RtlDispatchException/unwind
- [ ] win32u/user32/gdi32, message queues, desktop/window-station
- [ ] Kernelbase, KERNEL32, etc. as thin PE over ntdll
- [ ] Registry storage (system.reg/user.reg)
- [ ] Wow64 support (32-bit TEB/context, thunking)
- [ ] Graphics: wined3d or Vulkan-backed D3D, dxgi, dwrite/d2d, dcomp
